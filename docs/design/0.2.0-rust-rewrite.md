# meowctl 0.2.0 — Rust rewrite

**Status:** plan, not yet started.
**Baseline:** `v0.1.0` (Go, ~20k lines including tests).
**Goal:** the same product, rewritten in Rust, with the architecture corrected
along the way rather than transliterated.
**Repository conventions:** modelled on [`vlie`](https://github.com/retran/vlie).

---

## 1. Why rewrite, and what "same product" means

0.2.0 ships no new user-facing features. The `init.star` / `deps.mod` /
`deps.lock` / `pkgs.lock` / `state.toml` formats stay byte-compatible, the
Starlark API is unchanged down to the builtin signatures, the command surface
stays the same, and an existing dotfiles repo must apply identically under both
binaries. That constraint is what makes the rewrite verifiable: 0.1.0 becomes
the oracle.

**One deliberate exception: terminal output.** Rendering is the one surface
that is redesigned rather than ported — see §4. It is exempt from the parity
constraint because it is not an interface anything depends on, and because the
0.1.0 design leaks into the engine in a way the rewrite has to fix anyway.

What we actually get out of it:

- **One deployable artifact with no runtime assumptions.** Startup cost matters
  because `meowctl hook shell` runs on every shell spawn.
- **Types that encode the domain.** Most of the bug classes below are "a
  `string` was used where a `ComponentId`, `ModuleRef`, `Phase`, or a validated
  path belonged".
- **Effects behind traits.** Today most of the engine can only be tested by
  touching the real filesystem and spawning real processes.
- **Consistency with the rest of the workspace.** `vlie` is the reference for
  how Rust is organised here; meowctl joins it.

Rewriting is the right move over porting because the Go code's problems are
architectural, and a mechanical port would carry all of them across.

## 2. What is wrong with the 0.1.0 architecture

These are the specific defects the rewrite must fix. Each maps to a crate
boundary in §3.

| # | Defect | Where | Fix in 0.2.0 |
| --- | -------- | ------- | -------------- |
| 1 | `internal/cli` is a god-package: flag parsing, orchestration, lockfile I/O, module sync, apply planning, staleness computation, and phase running all live together (`lifecycle.go` 962 lines, `apply.go` 832) | `internal/cli` | `meowctl-cli` only maps clap → engine calls. Every decision moves into a domain crate. |
| 2 | Domain policy leaks into the CLI layer — `computeStaleComponents`, `resolveComponentVersions`, `clearStaleSentinels`, `readInstalledLock` are apply-engine logic living next to cobra commands | `internal/cli/apply.go` | `meowctl-engine` owns the apply plan as a value; the CLI renders it. |
| 3 | `ctx` mixes four concerns in one 1206-line file: Starlark value glue, filesystem mutation, process exec, and rollback journaling | `internal/ctx/methods.go` | Split: `meowctl-ops` (reversible operations), `meowctl-exec` (processes), `meowctl-fs` (filesystem trait), `meowctl-ctx` (thin Starlark binding). |
| 4 | Dry-run is `if c.caps.DryRun { … }` scattered through every effectful method — easy to miss one, and it has been missed (see `fix(apply): dry-run claimed work that the runner skips`) | `internal/ctx` | Dry-run is a `FileSystem`/`Executor` implementation, not a branch. A dry run is structurally incapable of writing. |
| 5 | Config edits are regex surgery on Starlark source, with a documented "kwarg order must be canonical" caveat | `internal/rewrite` | A syntax-aware editor over the parsed Starlark AST, preserving formatting and comments. |
| 6 | On-disk schemas are scattered: `lock`, `modfile`, `state`, plus ad-hoc `installed.lock` and `pkgs.lock` readers inside `cli` | 5 packages | One `meowctl-config` crate owning every file format, its schema version, and atomic writes. |
| 7 | Errors are formatted strings with an exit code attached (`exitErrorf(ExitConfig, …)`); Starlark failures carry no source spans | `internal/cli/errors.go` | `thiserror` enums per crate; one exit-code mapping at the binary; `miette` diagnostics with spans for Starlark errors. |
| 8 | Mutable package-level state: `var RootCmd = newRootCmd()`, version via `-ldflags` globals | `internal/cli/root.go`, `internal/version` | Commands constructed per invocation; version from `CARGO_PKG_VERSION` + build metadata. |
| 9 | Two-pass component evaluation is implicit — "pass one registers PM handlers" is a comment, not a type | `internal/cli/lifecycle.go` | Distinct `Discovered` → `Resolved` → `Planned` → `Executed` stages, each its own type. |
| 10 | Test suites reach for the real filesystem, network, and subprocesses; `RunFunc` injection exists only for `ctx.run` | throughout | Effects are traits; in-memory implementations for unit tests, real ones behind integration/corpus tests. |
| 11 | The engine holds a renderer. `buildRunner(…, w tui.Writer, …)` injects the TUI into the runner, and terminal ownership is then threaded back down as a `SuspendOutput func() (resume func())` callback through `ctx.Capabilities` — a renderer concern reaching into the Starlark layer | `internal/cli/lifecycle.go`, `internal/ctx` | The engine emits a typed event stream and holds no renderer. Terminal ownership is negotiated between renderer and executor, and the callback disappears. |
| 12 | Output is only ever text. `Writer.Log(format string, args ...any)` formats at the call site, so nothing downstream can restructure it; `doctor --json` is a hand-written special case and there is no machine-readable output anywhere else | `internal/tui`, `internal/cli/doctor.go` | Events are structured; text, JSON, and live rendering are three sinks over one stream. |

## 3. Target architecture

A Cargo workspace, `crates/` plus a thin root binary — the `vlie` layout.
Dependencies point strictly downward; no cycles.

```text
                        meowctl (bin)
                             │
                       meowctl-cli            clap surface, exit codes
                             │
                      meowctl-engine          phases, toposort, runner, planner, apply/verify/upgrade
                    ╱        │        ╲
        meowctl-module  meowctl-ctx   meowctl-pm       modules+MVS+loaders │ Starlark ctx │ PM dispatch
              │              │
        meowctl-starlark ────┤                         evaluator, builtins, accumulator, diagnostics
                             │
         meowctl-ops ── meowctl-exec ── meowctl-tui    reversible ops+WAL │ processes │ rendering
                    ╲        │        ╱
                       meowctl-fs                      FileSystem trait: real / dry-run / in-memory
                             │
                     meowctl-config                    every on-disk schema
                             │
                     meowctl-common                    ids, phases, paths, error taxonomy
```

### Crate responsibilities

| Crate | Owns | Replaces |
| ------- | ------ | ---------- |
| `meowctl-common` | `ComponentId`, `ModuleRef`, `Phase`, `PhaseSet`, XDG path resolution, the error/exit-code taxonomy, SRI hashes, the `Event` vocabulary | scattered `string` types, `internal/cli/errors.go` |
| `meowctl-config` | Schemas and atomic read/write for `init.star` declarations, `local.star`, `deps.mod`, `deps.lock`, `pkgs.lock`, `installed.lock`, `state.toml`; schema versioning and migration; the syntax-aware Starlark editor | `lock`, `modfile`, `state`, `rewrite`, lockfile code in `cli` |
| `meowctl-fs` | `trait FileSystem` with `RealFs`, `DryRunFs`, `MemFs`; path validation; atomic writes; symlink handling | implicit `os.*` calls everywhere |
| `meowctl-exec` | `trait Executor`, command construction, env merging, terminal hand-off for interactive hooks | `ctx.execRun`, `SuspendOutput` |
| `meowctl-ops` | The closed set of reversible operations (`WriteFile`, `Symlink`, `LinkFile`, `Mkdir`, `Download`, `DefaultsWrite`, `PlistSet`, …) as an enum with `apply`/`inverse`, and the write-ahead journal | `internal/rollback` + the effect half of `internal/ctx` |
| `meowctl-starlark` | Evaluator, predeclared builtins, declaration accumulator, `load()` resolution, span-carrying diagnostics | `internal/starlark` |
| `meowctl-module` | Module graph, MVS, registry and GitHub loaders, cache, integrity verification, `replace()` | `mvs`, `starlark/loader` |
| `meowctl-pm` | PM handler registry, `pkg`/`unpkg`/`uppkg`/`repo`/`query_pm` dispatch | `internal/pkg` |
| `meowctl-ctx` | The Starlark `ctx` value — binding only, every method delegating to `ops`/`exec`/`fs` | the binding half of `internal/ctx` |
| `meowctl-engine` | Component discovery, dependency graph, phase running, the apply plan as a value, sentinel state, staleness, rollback driving, **and emitting the `Event` stream** | `internal/lifecycle` + the orchestration half of `internal/cli` |
| `meowctl-tui` | Event sinks (live, plain, JSON), theme as data, capability detection, the `Interaction` trait for prompts | `internal/tui`, redesigned — see §4 |
| `meowctl-cli` | clap command tree, flag→request mapping, rendering results, exit codes | `internal/cli` (command definitions only) |
| `meowctl-xtask` | Dev tasks: compat corpus, release checks | new |

### Key design decisions

**Effects are traits, injected at the binary.** `FileSystem` and `Executor` are
constructed once in `main` from the flags (`--dry-run` selects `DryRunFs`) and
threaded down. No layer below `meowctl-cli` reads a global or checks a dry-run
flag. This is the single change that makes the engine unit-testable.

**Operations are data.** `meowctl-ops::Op` is an enum, not a set of methods.
`Op::inverse()` produces the undo record, `Op::apply(&dyn FileSystem)` performs
it, and the journal is a log of `Op`s. Adding an operation means adding a
variant, and the compiler then demands its inverse — today a new `ctx` method
can silently ship with no rollback support.

**The apply plan is a value.** `engine::plan(...) -> Plan` is pure given the
config and lock state; `engine::execute(plan, &effects)` runs it. `--dry-run`
prints the plan instead of executing it, which makes defect #4 impossible by
construction rather than by discipline.

**Staged types over staged comments.** `Discovered` → `Resolved` → `Planned`
makes the two-pass evaluation a type-level fact: PM handlers are registered on
`Resolved`, so a hook cannot run before registration.

**Sync I/O, no async runtime.** The network work is a handful of sequential
tarball fetches. `ureq` + `rustls` keeps startup cheap and avoids pulling tokio
through the whole tree; `meowctl hook shell` runs on every shell spawn.

### Dependency choices

| Need | Crate | Note |
| ------ | ------- | ------ |
| Starlark | `starlark` (starlark-rust) | **The main risk — see §5.** |
| CLI | `clap` (derive) | as in `vlie` |
| Errors | `thiserror`, `miette` | per-crate enums; `miette` for Starlark source diagnostics |
| TOML / serde | `toml`, `serde` | all lock and state files |
| Semver | `semver` | MVS ordering |
| HTTP | `ureq` + `rustls` | no async runtime |
| Hashing | `sha2`, `base64` | W3C SRI |
| Archives | `tar`, `flate2` | tarball extraction |
| Terminal | `anstyle`, `anstream`, `terminal-size`, `unicode-width` | ports the 0.1.0 design system; no TUI framework |
| Tests | `insta`, `assert_cmd`, `tempfile`, `proptest` | snapshots for rendering and CLI output |
| Runner | `cargo-nextest` | as in `vlie` |

## 4. Terminal output redesign

0.1.0's design system got the vocabulary right and the architecture wrong. The
three ideas in `internal/tui/theme.go` survive verbatim — one symbol vocabulary
across every command, never more than two levels of indent, and colour that is
always redundant to the wording — as does the rule that the live renderer never
takes raw mode, because hooks shell out to commands that need the real
terminal. Those are the reasons the output is readable today.

What does not survive is the shape. Two facts drive the redesign:

- The engine renders. `buildRunner` takes a `tui.Writer`, so producing progress
  and deciding how it looks are the same call. The consequence is visible in
  `ctx.Capabilities.SuspendOutput`: a renderer concern that had to be threaded
  into the Starlark layer as a callback so a subprocess could borrow the
  terminal (defect #11).
- Output is text at the point of production. `Log(format string, args ...any)`
  formats at the call site, which is why `doctor --json` is hand-written and
  why nothing else has a machine-readable form (defect #12).

### The redesign

**The engine emits events; it does not render.** The `Event` enum lives in
`meowctl-common` — the shared vocabulary belongs below both the producer and
the consumers, so a sink never depends on the engine. `meowctl-engine` produces
the stream — `PhaseStarted`, `ComponentStarted`, `ComponentFinished { outcome }`,
`OpApplied`, `ProcessOutput { stream, line }`, `Diagnostic`, `PlanComputed`,
`Message { severity, .. }` — and knows nothing about terminals. Renderers are
sinks over that stream.

Terminal ownership follows from it: an interactive hook emits
`TerminalRequested`, the sink stands down and erases its region, and
`TerminalReleased` brings it back. The negotiation is between the executor and
the sink, so `SuspendOutput` disappears from `ctx` entirely — it only ever
existed to paper over the engine holding a renderer.

**Three sinks, one stream.**

| Sink | When | Notes |
| ------ | ------ | ------- |
| `LiveSink` | TTY with motion | In-place progress, spinner, region erasure, terminal hand-off |
| `PlainSink` | Pipe, CI, `TERM=dumb`, `MEOWCTL_OUTPUT=plain` | Append-only lines, same vocabulary, no motion |
| `JsonSink` | `--format json` | One JSON object per event, per line |

`JsonSink` is the part that pays for itself immediately: `doctor --json` stops
being a special case, every command gains machine-readable output for free,
and `cargo xtask compat` (M1) can diff two runs structurally instead of
scraping rendered text.

**Structured messages.** Free-form `Log(format, args)` is gone. Anything worth
printing is an event variant; genuinely unstructured text goes through
`Message { severity, text }`, and severity — not the call site — decides
whether it lands on stdout, stderr, or nowhere.

**Theme as data.** The Catppuccin palette stays the default, but as values in
a theme file rather than truecolor SGR constants compiled into the binary.
Users can point at their own; roles stay semantic, so no call site ever names
a colour. Downsampling to 256/16/mono stays automatic.

**Prompts leave the printer.** `Printer.Confirm` mixes input into an output
type. An `Interaction` trait (`confirm`, `select`) replaces it, with a
non-interactive implementation that fails loudly rather than hanging — a CI run
that hits a prompt should die with a clear message, not block until timeout.

**Progress that reflects the model.** The engine's unit of work is a component
within a phase, but packages within a component are invisible today — a
component installing forty packages looks identical to one installing none.
The live sink shows sub-work on the component's own status line rather than by
indenting further, which keeps the two-level rule intact.

### Verification

Snapshot tests (`insta`) over a recorded event stream, rendered through each
sink across every cell of the capability matrix: motion × colour depth × glyph
tier × width. The stream is a fixture, so the tests need no terminal, no
subprocess, and no filesystem — which is what makes it feasible to enumerate
the matrix at all, rather than spot-checking two or three cases as the Go tests
do.

## 5. The one real risk: Starlark dialect parity

0.1.0 runs `go.starlark.net`. 0.2.0 would run `starlark-rust`. They are
independent implementations of the same spec with different extension points,
and the parity questions are load-bearing for this project specifically:

- `load()` interception — the composite loader (filesystem / registry /
  GitHub-with-integrity-check) must map onto starlark-rust's `FileLoader`.
- Custom values with attributes — `ctx` is a `HasAttrs` value in Go; the
  equivalent is `StarlarkValue` with `get_attr`, plus lifetime constraints Go
  did not impose.
- Per-thread state — the Go builtins reach the accumulator and `ctx` through
  `thread.SetLocal`; starlark-rust has `Evaluator::extra`, which is a
  `&dyn Any` with a lifetime attached.
- `struct` and `select()` semantics, string formatting, integer behaviour, and
  the exact text of runtime error messages (which appear in test snapshots).
- Calling a Starlark function from Rust with a custom argument — how every hook
  is invoked.

**M0 has run, against `starlark` 0.14.2, and every question above is
answered.** The extension points cover all five: `FileLoader` for the composite
loader, `StarlarkValue` with `get_attr` and a `MethodsStatic` block for `ctx`,
`Evaluator::extra` for per-evaluation state, `eval_function` for calling a hook
with a custom argument, and `Error::span` for a diagnostic that already renders
a caret under the offending source. The findings, and the two binding
constraints they impose, are in `docs/spec/starlark.md`.

Two things the spike changed. The evaluator's heap is scoped to a closure —
`Module::with_temp_heap(|module| ...)` — so nothing Starlark allocated escapes
an evaluation, which makes the accumulator's owned-data rule something the
compiler enforces rather than a discipline. And runtime error text differs from
`go.starlark.net`; the decision to accept the library's wording is argued in
`docs/design/0.2.0-decisions.md` §3.11.

The alternatives the spike existed to price — vendoring a patched
starlark-rust, or writing the evaluator in-house — are not needed.

Secondary risks, each with a named mitigation:

- **Format drift** — a serde round-trip that reorders lock keys breaks
  reproducibility. Mitigated by byte-identical golden files from 0.1.0 (M1).
- **Rendering drift** — the live writer is subtle (region erasure, terminal
  hand-off, capability degradation). Mitigated by `insta` snapshots taken from
  the Go binary across each capability matrix cell.
- **Scope creep** — "while we are in here" is how a rewrite becomes an
  18-month project. The §2 defect list is the whole licence to change design;
  anything else is an issue against 0.3.0.

## 6. Milestones

Bottom-up, each milestone independently mergeable and green in CI. The Go
binary stays in the tree and buildable until M9.

### M0 — Starlark spike *(done)*

Proved all five bindings against `starlark` 0.14.2: a custom `ctx`-like value
with attributes and methods, `load()` routed through a custom loader,
per-evaluation state reachable from a builtin, calling a Starlark function from
Rust with a custom argument, and a diagnostic with a source span.

The findings are in `docs/spec/starlark.md`, and none contradicted the design.
One check from this milestone remains: evaluating the real `meowctl-stdlib`
component files unchanged needs the builtin set, so it moves into M4.

### M1 — Workspace skeleton and compatibility corpus

Cargo workspace, `rust-toolchain.toml`, `.cargo/config.toml` (`xtask` alias),
`mise.toml` tasks mirroring `vlie` (`check`, `build`, `test`, `fmt`, `watch`,
`lint-md`), CI jobs (check, clippy `-D warnings`, nextest, fmt, docs,
markdown), and `CONTRIBUTING.md`. The agent harness — `CLAUDE.md`,
`.claude/`, `docs/README.md`, `docs/spec/README.md` — already exists on this
branch; M1 only updates its `<build>` section once the mise tasks are real.

Then the oracle: `cargo xtask compat` records the 0.1.0 binary's output and
resulting file trees over a set of real configs (`dotmeow`, `meowctl-stdlib`,
`testdata/smoke`) as golden fixtures — the `vlie` `check-corpus` pattern.

**Done when:** `mise run test` is green and the golden corpus is committed.

### M2 — `meowctl-common` + `meowctl-config`

Domain types, error taxonomy, exit codes. Every on-disk schema with serde, and
byte-identical round-trips against the M1 golden files. Syntax-aware Starlark
editing replacing `internal/rewrite`, with property tests for
comment/formatting preservation.

### M3 — `meowctl-fs`, `meowctl-exec`, `meowctl-ops`

`FileSystem` and `Executor` traits with real, dry-run, and in-memory
implementations. The full `Op` enum with `apply`/`inverse`, and the WAL journal
reading 0.1.0's journal format. Property test: apply-then-undo on `MemFs`
restores the original tree, for every variant.

### M4 — `meowctl-starlark`

Evaluator, the full predeclared set, accumulator, `select`/`platform`,
composite `load()` resolution, span-carrying diagnostics. Runs every
`meowctl-stdlib` component to the same declarations as 0.1.0.

### M5 — `meowctl-module` + `meowctl-pm`

MVS (unit tests ported directly — the Go tests are good), registry and GitHub
loaders, cache, SRI verification, `replace()`. PM registry and dispatch.

**Done when:** `meowctl dep sync` produces a lock file byte-identical to
0.1.0's on the corpus.

### M6 — `meowctl-ctx`

The `ctx` value, delegating to M3. Restricted `ctx` for read-only phases.
Templating, `emit`, `add_path`, `prompt`.

### M7 — `meowctl-tui` (redesign, not a port)

The event stream and its three sinks, per §4: `LiveSink`, `PlainSink`,
`JsonSink`; theme loaded as data; the `Interaction` trait. `insta` snapshots
over a fixture event stream across the full capability matrix.

**Done when:** every command's output is produced by a sink over the event
stream, `--format json` works everywhere, and `SuspendOutput` exists nowhere in
the tree.

### M8 — `meowctl-engine`

Phase sets, dependency graph and toposort, the staged pipeline, `Plan` as a
value, the runner, sentinel state, staleness detection, rollback driving.

### M9 — `meowctl-cli` and cutover

Full clap surface, exit-code mapping, shell completions. `cargo xtask compat`
passes against the recorded 0.1.0 behaviour on every corpus config. Then:
delete `cmd/`, `internal/`, `go.mod`, `go.sum`, `.golangci.yml`; rewrite the
README; release 0.2.0 with the Rust cross-platform build matrix.

**Done when:** the Go tree is gone and a real machine applies its dotfiles with
the Rust binary.

## 7. Sequencing notes

- **M0 is done.** It gated the rest and no longer does.
- M2 and M3 are independent of each other and can run in parallel.
- M4 depends on M0's findings, now recorded, and on M2's config types.
- M7 is independent of M4–M6 and can be picked up whenever: the `Event`
  vocabulary lives in `meowctl-common`, so the sinks never depend on the
  engine that emits into it.
- M8 is the integration point and needs M3–M7 complete.
- Keep the Go binary building through M8 — it is the oracle, and deleting it
  early removes the only thing that proves parity.

## 8. Explicitly out of scope for 0.2.0

New commands; changes to the Starlark API surface; config format changes;
parallel component execution; a daemon or server mode; Windows support beyond
what 0.1.0 already builds. Each is a 0.3.0 conversation, after parity is
proven.

Terminal output is the one exception, redesigned under §4 — but that redesign
is bounded by what §4 names. A full-screen TUI, a component browser, or
anything requiring raw mode is out: hooks need the real terminal, and the
never-raw-mode rule is load-bearing, not a limitation to be lifted.
