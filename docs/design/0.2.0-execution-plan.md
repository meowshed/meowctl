# Execution plan

This decomposes the 308 requirements in `docs/spec/` into issues with explicit
dependencies. `0.2.0-rust-rewrite.md` §6 sets the milestone order and
`0.2.0-decisions.md` argues the choices; this says what to build, in what
order, and how each piece is known to be done.

Every requirement lands in exactly one issue. The coverage table in §5 is the
check on that, and it is the thing to update whenever an issue is split.

## How to read an issue

Each carries its requirement IDs verbatim, its blockers, and a size: **S** is
reviewable in one sitting, **M** in one careful sitting, **L** should probably
have been split and is marked so on purpose.

Issues are cut by vertical slice rather than by layer. An issue that adds a
type to `meowctl-common` and nothing else cannot be reviewed on its merits,
because nothing it does is observable.

## 2. The issues

### M1 — the oracle

**Issue 1. Record the v0.1.0 compat corpus.** *(M, no blockers) — done*

Closes [R-CLI-040], [R-CLI-041], [R-CLI-042], [R-CLI-043], [R-CLI-044].

`cargo xtask compat` runs a recorded command list against a set of
configurations under the `v0.1.0` binary and stores the resulting file tree,
every file meowctl wrote, and the exit code as golden fixtures. Rendered text
is not compared.

`verify` is not in the list, and no command that evaluates hooks runs against a
configuration outside this repository. A hook runs whatever the configuration
says, and the standard library's `verify` hooks call `open -a <App>`.

This comes first because it is the only thing that can tell us the rewrite is
correct, and because recording it against a binary that already works is
cheaper than recording it later against one that half works.

**Done when:** the corpus runs green against `v0.1.0` twice in a row, and a
deliberately corrupted fixture makes it fail with a diff naming the file.

Both hold. Two findings changed the design while building it. Fixtures are
keyed by platform, because the corpus compares two binaries on one machine and
a macOS recording checked on Linux reports platform differences as rewrite
defects. And three paths and two build details are normalised, without which
two recordings of one command never match; `tests/compat/README.md` says what
that hides and why it is still worth doing.

### M2 — vocabulary and formats

Closes [R-COMMON-001] through [R-COMMON-004], [R-COMMON-010] through

**Issue 3. The event vocabulary.** *(S, blocked by 2)*

Closes [R-COMMON-040] through [R-COMMON-043].

The `Event` enum and its JSON form. Observable through a test that serializes
one of each variant.

**Issue 4. Lock files.** *(M, blocked by 2, 10) — done*

Closes [R-CONFIG-020] through [R-CONFIG-025], [R-CONFIG-061].

Read and write `deps.lock`, `deps.local.lock`, `pkgs.lock`, `pkgs.local.lock`.
Checked against the M1 fixtures byte for byte.

**Issue 5. Sentinel state.** *(S, blocked by 2, 10) — done*

Closes [R-CONFIG-040] through [R-CONFIG-044].

Includes [R-CONFIG-041], refusing to overwrite a newer schema version, which is
decided in §3.8 of the decisions document and needs a test that writes a future
version and asserts the refusal.

**Issue 6. installed.lock, both schema versions.** *(S, blocked by 2, 10) — done*

Closes [R-CONFIG-030] through [R-CONFIG-033].

The version 1 form must still parse; a fixture in the old form is part of the
issue.

**Issue 7. deps.mod reading and writing.** *(S, blocked by 2, 16) — done*

Closes [R-CONFIG-010] through [R-CONFIG-014].

Smaller than it looked. Reading `deps.mod` is evaluating it, which
`meowctl-starlark` already does: `dep()`, `module()` and `replace()` are in the
accumulator, and the engine hands what comes back to `meowctl-config`. So this
issue is the writer and the byte-exact layout, which the emitter already has
the shape for.

`meowctl-config` does not gain a dependency on `meowctl-starlark` for this.

**Issue 8. The syntax-aware Starlark editor.** *(M, blocked by 7) — done*

Closes [R-CONFIG-050] through [R-CONFIG-053].

Medium rather than large, and for a reason worth recording: the first sizing
assumed formatting preservation needed a printer, and it does not. The edit is
made to the *text*, at the position the parse reports. Nothing is re-rendered,
so nothing can be lost, and the property test proves the untouched bytes are
untouched rather than proving a printer round-trips.

`meowctl-config` gains a dependency on the `starlark` crate for its parser —
an external dependency of the same shape as `toml`, not an edge to
`meowctl-starlark`. The design note under §3's crate table says why that is a
design question rather than a rule violation, and [R-CONFIG-010] now says which
of parsing and evaluating happens where.

The cost is that the dialect is named in two crates. A test runs one file
through both, because a file the editor accepts and the evaluator rejects means
`meowctl add` succeeding on a configuration that then fails to apply.

**Issue 9. Config layout and the legacy check.** *(S, blocked by 2) — done*

Closes [R-CONFIG-001] through [R-CONFIG-004], [R-CONFIG-060],
[R-CONFIG-062], and [R-CONFIG-063].

The three added here were claimed by no issue and are properties of every
format rather than of one: writes go through `FileSystem`, a failed write
leaves the previous file, and two runs cannot interleave. [R-FS-003]'s atomic
rename is what provides all three, so the work is the tests that say so.

### M5 — modules and package managers

**Issue 19. Fetching, integrity, and the cache.**
*(L on purpose, blocked by 4, 10) — done*

Closes [R-NET-001] through [R-NET-006], [R-NET-010] through [R-NET-014],
[R-COMMON-005], [R-FS-005], [R-FS-006],
[R-MODULE-010] through [R-MODULE-013],
[R-MODULE-030] through [R-MODULE-034],
[R-MODULE-040] through [R-MODULE-045], [R-MODULE-060],
[R-MODULE-063], and [R-STAR-020] through [R-STAR-022].

Large because integrity, extraction, and caching are one path: a slice that
fetches without verifying is a slice that must not ship. It carries three
things the plan did not originally put here.

`meowctl-net` is one of them: the network is the third effect behind a trait,
and it has to exist before anything fetches. The decision is in
`0.2.0-decisions.md` §2.

[R-STAR-020] and [R-STAR-021] are the second. Issue 16 was recorded as closing
them and closed neither: it delivered the `Loader` trait, the evaluation cache,
and the load chain in diagnostics, which is what [R-STAR-023] and [R-STAR-053]
needed, and left every scheme unresolved because nothing could yet fetch one.
The composite loader lands here, where the schemes it dispatches to exist.

[R-FS-005] is the third, and it is small: extraction has to set an executable
bit, and doing that outside the `FileSystem` trait is a filesystem effect a dry
run cannot see.

**Issue 20. Version selection.** *(M, blocked by 2) — done*

Closes [R-MODULE-001] through [R-MODULE-005], [R-MODULE-061], [R-MODULE-062].

The Go tests in `internal/mvs/mvs_test.go` port directly and should.

**Issue 21. Locking, syncing, and overrides.** *(M, blocked by 19, 20) — done*

Closes [R-MODULE-020] through [R-MODULE-022], [R-MODULE-050] through
[R-MODULE-053], [R-MODULE-064].

**Done when:** a sync produces a lock byte-identical to `v0.1.0`'s from the
same manifest against the same registry.

The corpus cannot check this: it runs no command that reaches a registry, on
purpose. The oracle is a fixture instead, written by `v0.1.0`'s own
`SyncModules` against a scripted registry, with the tarballs it hashed checked
in beside it. `TestWriteSyncFixture` in `internal/starlark/loader` regenerates
all three.

The comparison excludes `meta`, which is the one table the two binaries are
meant to disagree about; see [R-CONFIG-022].

**Issue 22. The package-manager registry.** *(M, blocked by 14) — done*

Closes [R-PM-001] through [R-PM-004], [R-PM-010] through [R-PM-014],
[R-PM-020], [R-PM-030] through [R-PM-032], plus [R-STAR-005] and
[R-STAR-033].

[R-STAR-005] is `query_pm`, which issue 14 was recorded as closing under
[R-STAR-001] and left out: it is the one builtin that runs user code during
evaluation, and it cannot be written before there is a registry to ask.
[R-STAR-033] is what registration reads.

[R-PM-003], [R-PM-015] and [R-PM-021] move to issue 30. All three are
statements about when a handler is called rather than about what is called:
registration finishing before any hook runs, declarations dispatching in graph
order, and `interrogate` being allowed during a dry run. This crate produces a
call; the runner makes it.

person.

## 4. What must be decided before the first issue

Nothing. M0 closed the four questions that were open, and
`0.2.0-decisions.md` records the thirty choices the specs make. The first
issue is the corpus, and it depends on the Go binary, which is tagged.

## 5. Coverage

Every requirement in `docs/spec/` appears in exactly one issue above. Three
issues close no requirement and exist to verify: issue 18 checks the stdlib
evaluates identically, issue 33 checks the corpus, and issue 34 removes the
oracle once it has done its work.

When an issue is split, move its requirement IDs rather than duplicating them,
and check the total still comes to 308. `/verify` reports a requirement that no
test references; it cannot report a requirement that no issue claims, which is
what this section is for.
