# Execution plan

This decomposes the 322 requirements in `docs/spec/` into issues with explicit
dependencies. `0.2.0-rust-rewrite.md` §6 sets the milestone order and
`0.2.0-decisions.md` argues the choices; this says what to build, in what
order, and how each piece is known to be done.

Every requirement lands in exactly one issue. The coverage table in §5 is the
check on that, and it is the thing to update whenever an issue is split.

## How to read an issue

Each carries its requirement IDs verbatim, its blockers, and a size: **S** is
reviewable in one sitting, **M** in one careful sitting, **L** should probably
have been split and is marked so on purpose.

Issues are cut by vertical slice rather than by layer. An issue that adds a
type to `meowctl-common` and nothing else cannot be reviewed on its merits,
because nothing it does is observable.

## 2. The issues

### M1 — the oracle

**Issue 1. Record the v0.1.0 compat corpus.** *(M, no blockers) — done, then
deleted by issue 34*

Closed the five requirements that described the corpus. Issue 34 deleted them
along with it, so they are no longer in `docs/spec/cli.md`; what follows is the
record of what the corpus was for.

`cargo xtask compat` runs a recorded command list against a set of
configurations under the `v0.1.0` binary and stores the resulting file tree,
every file meowctl wrote, and the exit code as golden fixtures. Rendered text
is not compared.

`verify` is not in the list, and no command that evaluates hooks runs against a
configuration outside this repository. A hook runs whatever the configuration
says, and the standard library's `verify` hooks call `open -a <App>`.

This comes first because it is the only thing that can tell us the rewrite is
correct, and because recording it against a binary that already works is
cheaper than recording it later against one that half works.

**Done when:** the corpus runs green against `v0.1.0` twice in a row, and a
deliberately corrupted fixture makes it fail with a diff naming the file.

Both hold. Two findings changed the design while building it. Fixtures are
keyed by platform, because the corpus compares two binaries on one machine and
a macOS recording checked on Linux reports platform differences as rewrite
defects. And three paths and two build details are normalised, without which
two recordings of one command never match.

**Issue 7. deps.mod reading and writing.** *(S, blocked by 2, 16) — done*

Closes [R-CONFIG-010] through [R-CONFIG-014].

Smaller than it looked. Reading `deps.mod` is evaluating it, which
`meowctl-starlark` already does: `dep()`, `module()` and `replace()` are in the
accumulator, and the engine hands what comes back to `meowctl-config`. So this
issue is the writer and the byte-exact layout, which the emitter already has
the shape for.

`meowctl-config` does not gain a dependency on `meowctl-starlark` for this.

**Issue 8. The syntax-aware Starlark editor.** *(M, blocked by 7) — done*

Closes [R-CONFIG-050] through [R-CONFIG-053].

Medium rather than large, and for a reason worth recording: the first sizing
assumed formatting preservation needed a printer, and it does not. The edit is
made to the *text*, at the position the parse reports. Nothing is re-rendered,
so nothing can be lost, and the property test proves the untouched bytes are
untouched rather than proving a printer round-trips.

`meowctl-config` gains a dependency on the `starlark` crate for its parser —
an external dependency of the same shape as `toml`, not an edge to
`meowctl-starlark`. The design note under §3's crate table says why that is a
design question rather than a rule violation, and [R-CONFIG-010] now says which
of parsing and evaluating happens where.

The cost is that the dialect is named in two crates. A test runs one file
through both, because a file the editor accepts and the evaluator rejects means
`meowctl add` succeeding on a configuration that then fails to apply.

**Issue 9. Config layout and the legacy check.** *(S, blocked by 2) — done*

Closes [R-CONFIG-001] through [R-CONFIG-004], [R-CONFIG-060],
[R-CONFIG-062], and [R-CONFIG-063].

The three added here were claimed by no issue and are properties of every
format rather than of one: writes go through `FileSystem`, a failed write
leaves the previous file, and two runs cannot interleave. [R-FS-003]'s atomic
rename is what provides all three, so the work is the tests that say so.

**Issue 35. The commands that write a configuration.**
*(M, blocked by 32) — done*

`init`, `add`, `remove`, `update`, `self-update`, and `dep add`, `dep remove`

**Issue 33. Corpus parity.** *(M, blocked by 32) — done*

Closes no requirement. `cargo xtask compat` passes against the recorded
`v0.1.0` behaviour on every corpus configuration. Every difference is a finding
against the issue that owns the requirement, not a new requirement here.

Three configurations and twenty-eight cases: the smoke corpus, an empty
directory so `init` has somewhere to scaffold, and a real one through
`MEOWCTL_COMPAT_EXTRA`. A foreign configuration runs only the commands that
call no hook, because a hook runs whatever its author wrote.

`check` is what makes a real configuration worth pointing at: it evaluates
every component file without calling a hook, so the whole evaluator is
compared against somebody's actual components. It found two differences, both
in this tree: a missing directory reported as zero files rather than as a
mistake, and the wrong exit code for it.

**Issue 34. Cutover.** *(M, blocked by 33, 35) — done*

Closed the requirement that said the corpus had an end date, by carrying it
out.

Deletes `cmd/`, `internal/`, `go.mod`, `go.sum`, `.golangci.yml`, the Go CI
workflow, the Go tasks in `mise.toml`, and the Go hooks in
`.pre-commit-config.yaml`. Rewrites the README. `meowctl-xtask` goes too: the
corpus was the only task in it.

The corpus goes with them, and so do the five requirements that described it.
It existed to prove that `v0.2.0` does what `v0.1.0` did, and once that is
proved it becomes a brake: every deliberate improvement after the cutover would
have to be argued past an oracle that says the old behaviour is correct, and
producing the oracle means keeping the Go tree buildable. Parity is the
constraint of the rewrite, not of the tool.

Three fixtures survive, moved to `crates/meowctl-module/tests/fixtures/`: a
`deps.lock` that `v0.1.0` wrote and the two tarballs it hashed. They are not an
oracle any more, because nothing regenerates them. They are the lock format
itself, which [R-CONFIG-023] freezes whatever happens to the binary that first
wrote it.

**Done when:** a real machine applies its dotfiles with the Rust binary.

Both binaries were run against the same live configuration before the Go tree
went. They discover the same graph: `v0.1.0` prints the components absent from
`installed.lock` and `v0.2.0` prints the whole graph with a status each, which
is why the two counts differ and neither list holds a component the other
missed.

**Issue 36. The runtime hooks.** *(M, blocked by 34) — done*

Closes [R-CLI-060] through [R-CLI-065], [R-CLI-070], [R-CLI-071],
[R-ENGINE-035], [R-CONFIG-064], [R-TUI-013], and [R-COMMON-023].

Found after the cutover, which is where it should have been found before it.
`hook <phase>` was a stub, and `meowctl shell <shell> | source` calls
`meowctl hook shell` on every shell spawn -- so a machine switched to `v0.2.0`
lost its PATH, its `mise`, its `starship`, its `direnv` and every environment
variable its components contribute. Nothing in the corpus covered it, because
the corpus runs commands against a sandbox and `hook` produces its output from
the hooks of real components.

Two requirements that already existed turned out to be wrong rather than
merely unimplemented. [R-CTX-002] said `ctx.shell` is `None` "outside
`shell.star` evaluation"; there is no file by that name, the phases are
`shell` and `login`, and reading it literally sent the first implementation to
`None` everywhere, so every component that branches on the shell emitted
nothing. [R-CTX-031]'s restricted surface was never wired up: `Surface::Shell`
existed and `Surface::for_phase` never returned it. Both are amended, and
every `shell` and `login` hook in `meowctl-stdlib` and in `dotmeow` was
checked against the eight attributes before the restriction was enforced.

[R-CLI-070] is the other kind of finding. `v0.1.0`'s `self-update` renames an
unverified download over the running binary and its own source says the
verification is deferred. That is not reproduced: the requirement says what it
has to do instead, and [R-CLI-071] says what it does until a release publishes
a checksum.

[R-COMMON-023] came out of the same work, from the other direction. These are
the first tests that run the binary rather than call a function, and they
failed on Windows because `home_dir` read only `$HOME`. `os.UserHomeDir`,
which `v0.1.0` calls, reads `$USERPROFILE` there. Every invocation on Windows
had been failing before it did anything, and nothing had noticed because
nothing had started the process.

**Done when:** `meowctl hook shell` and `meowctl hook login` produce the same
bytes as `v0.1.0` against a real configuration. Both do.

**Issue 37. The flag surface `v0.1.0` actually has.** *(S, blocked by 36) — done*

Closes [R-CLI-015] and [R-CLI-016], and corrects [R-CLI-005].

`/verify` found it. [R-CLI-005] said `--dry-run` on "each mutating command"
and `--force`, `--no-rollback` and `--ignore-lock` on `apply`. The two helpers
in `internal/cli/lifecycle.go` are the real grouping: `addLifecycleFlags`
gives `--dry-run`, `--no-rollback` and `--verbose` to all six lifecycle
commands, and `addInstallFlags` gives `--force` and `--ignore-lock` to
`apply`, `add` and `upgrade`. The requirement was written from `apply`, the
implementation followed it, and five commands shipped without
`--no-rollback`, two without `--force`, and `verify` without `--dry-run`.

The test was the reason it survived: it checked `--dry-run` on six commands
and the other three on `apply` alone, so every missing flag was outside what
it looked at. It now walks the table.

[R-CLI-016] records the other half of the finding. `--ignore-lock` reaches no
code path in either binary: `v0.1.0` declares it on `runConfig` and never
reads it. It was reported as a divergence and is not one -- it is parity with
a flag that has never done anything. Dropping it would break a script that
passes it, so it stays, and the requirement says it is inert rather than
leaving that to be inferred from a help string.

**Done when:** the flag table matches `v0.1.0` command for command. It does.

**Issue 38. The package locks.** *(M, blocked by 36) — done*

Closes [R-CONFIG-026] and [R-CONFIG-027], and implements [R-CONFIG-025],
which nothing did.

`/verify` found it: `PackageEntry`, `LockFile.packages` and the two layout
paths all existed and were parity-tested for format, and no command ever
called them. `v0.1.0` ends `runApply` with `appendPkgsLock`; `v0.2.0` ended it
with nothing. A machine switched over stopped updating a file it had been
writing since `v0.1.0`.

The collection belongs to the engine and the writing to the CLI: `Report`
gains the declarations of every component whose `install` or `upgrade` ran,
and nothing below `meowctl-cli` learns where the configuration directory is.
Which of the two files a component lands in is decided by which entry point
declared it, which is the one thing the split turns on -- getting it backwards
commits a machine's private packages to a shared repository.

Two corrections came with it. [R-CONFIG-025] said "resolved package
installations", and the file resolves nothing: `v0.1.0` writes the declared
constraint as both `requested` and `installed`. And [R-CONFIG-027] says these
two are not byte-compared, because `v0.1.0` writes them with a different
encoder than the one [R-CONFIG-023] freezes for `deps.lock`.

**Done when:** a run that declares packages writes both files, split by
declaring entry point, and a run that declares none writes neither.

**Issue 39. The failure paths nothing was checking.** *(M, blocked by 36) — done*

Implements [R-CONFIG-061], and gives [R-OPS-005], [R-OPS-026], [R-OPS-032]
and [R-NET-005] the tests they never had.

`/verify` counted coverage by looking for a requirement identifier in a test,
and found 88 of 318 with none. Most turned out to be cited on the
implementation instead of on a test, or covered by a neighbour's test. These
five were the ones where being unchecked was worth something.

[R-OPS-005] is the one that mattered. An `Op` that finds the system already in
its target state must still produce a correct inverse -- re-linking a symlink
that already points where the component wants it is the ordinary case on a
second `apply`, and an inverse of `Remove` there would make the next rollback
delete a link the user depends on. The code was right. The property strategy
seeded a tree and applied one operation to it, so it could never reach the
state where the operation had already happened, and the case was untested.
Removing the branch now fails two tests instead of none.

[R-CONFIG-061] was not implemented at all. `ModuleEntry.integrity` is a
`String` and never went through `Integrity`, so a lock naming a hash of
`not-a-hash` parsed cleanly and failed later as a mismatch -- which is how
tampering looks, for a file somebody hand-edited.

**Done when:** each of the five fails when the behaviour it names is removed.
Checked by removing it.
