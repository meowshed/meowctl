# Decisions and trade-offs

This document accounts for every requirement in `docs/spec/`. A specification
states obligations; it does not argue for them, and a reader who wants to know
why an obligation is what it is has nowhere to look. This is that place.

## How every requirement is accounted for

There are 304 requirements. They fall into three kinds, and the kind decides
whether a trade-off exists to analyse.

- **Decided.** A different answer was available. There are 39 of them: the ones
  argued in §3, and the ones that follow directly enough from an architecture
  decision in §2 to be reviewable against it. `0.2.0-requirement-tradeoffs.md`
  marks each with a **D**, and the two lists are checked against each other.
  There is also one decision about Starlark error text that constrains
  `docs/spec/starlark.md` without being a single requirement.
- **Derived.** The requirement follows from an architecture decision in §2. The
  trade-off was taken once, at the decision, and analysing it again per
  requirement would restate the same argument.
- **Transcribed.** The requirement states what `v0.1.0` already does. Parity is
  the contract, so there was no choice to make: the only way such a requirement
  is wrong is by misreading the Go source.

The remaining 250 are derived or transcribed. Their grounding is visible in the
files: 32 cite the Go file they were read from in the requirement itself, and
the rest are covered by their file's "Parity with `v0.1.0`" section, which names
what was reproduced and what was deliberately changed.

That split is not audited per requirement, and it would be worth auditing if
the specs were ever cited as evidence that nothing changed. `/verify` does the
useful half already: for a requirement that cites `v0.1.0` behaviour, it
re-reads the Go code and reports a parity claim that does not hold.

## 1. What is not up for decision

Three things are settled by the plan rather than by this document, and every
requirement that follows from them is derived rather than decided.

**Parity is the contract.** The Starlark API, the command surface, and every
config and lock format stay compatible. The alternative, a rewrite that also
improves the surface, was rejected in `0.2.0-rust-rewrite.md` §1 for a reason
that holds here: parity is what makes the rewrite verifiable, because `v0.1.0`
becomes an oracle that can be diffed against. Give that up and the only way to
know the rewrite is correct is to read it.

**Terminal output is the one carve-out.** Argued in §4 of the plan.

**The crate boundaries.** Argued in §3 of the plan.

## 2. Architecture decisions, and what each costs

These were taken in the plan; what follows is the cost side, which a plan that
is selling a direction tends to under-state.

### Effects behind traits

**Decision.** `FileSystem` and `Executor` are constructed at the binary and
passed down; a dry run is a different implementation.

**Alternative.** Keep the `v0.1.0` shape: a `dry_run` flag in a context struct,
checked where it matters.

**What it costs.** Every function that touches the filesystem grows a
parameter, and a trait object has a virtual call where `v0.1.0` had a direct
one. In a tool that spends its time waiting on subprocesses and the network,
the virtual call is not measurable; the parameter is real and shows up in
signatures throughout `meowctl-ops` and `meowctl-engine`.

**Why anyway.** `fix(apply): dry-run claimed work that the runner skips` is the
bug this prevents, and it is a bug of a kind that recurs: the guarantee "a dry
run writes nothing" held only as long as every author remembered a branch. It
also buys the engine's testability, which is what makes [R-OPS-004] and
[R-ENGINE-002] checkable at all.

**What would reverse it.** A measurement showing the indirection costs
something on `meowctl hook shell`, which is the one latency-sensitive path.

### Operations as data

**Decision.** Every reversible effect is a variant of `Op` with an `inverse`.

**Alternative.** Methods that perform an effect and separately append to a
journal, as `v0.1.0` does.

**What it costs.** A closed enum. Adding an effect means touching the enum, its
apply, its inverse, and the journal's serialization, where `v0.1.0` needed one
new method. It also means an effect that genuinely cannot be undone has nowhere
to live without a variant that lies about having an inverse.

**Why anyway.** The `v0.1.0` arrangement lets a new `ctx` method ship with no
rollback and nothing notices until a failed run leaves a machine half
configured. The enum makes the compiler ask.

**What would reverse it.** An effect that must be supported and cannot be
inverted. `defaults_write` came close, and [R-OPS-017] resolves it by recording
the prior value; an effect with no readable prior state would not have that
escape.

### The engine emits events and holds no renderer

**Decision.** `meowctl-engine` produces `Event`s; sinks consume them.

**Alternative.** Pass a writer into the runner, as `v0.1.0` does.

**What it costs.** An indirection between producing a fact and showing it, and
a vocabulary that has to be designed up front. A sink that wants a detail the
engine does not emit cannot reach for it; the event has to be added.

**Why anyway.** Defect #11 is the concrete cost of the alternative:
`buildRunner` takes a `tui.Writer`, and the consequence is `SuspendOutput`, a
renderer concern threaded into the Starlark layer as a callback so a subprocess
could borrow the terminal. It also buys `JsonSink`, which is what lets the
compat corpus diff two runs structurally instead of scraping rendered text.

**What would reverse it.** Nothing short of the event vocabulary proving unable
to express something a user needs to see, which would be an amendment rather
than a reversal.

### No async runtime

**Decision.** `ureq` and `rustls`, no tokio.

**Alternative.** `reqwest` with tokio, which is the default choice for HTTP in
Rust and brings connection reuse and concurrency for free.

**What it costs.** Module fetches are sequential. A configuration with twenty
modules pays twenty round trips in series where a concurrent fetch would
overlap them.

**Why anyway.** `meowctl hook shell` runs on every shell spawn, and a runtime
initialised on every interactive shell is a cost paid thousands of times a day
to save seconds on a sync that happens weekly. The asymmetry is large enough
that the sequential fetch is the cheaper end of it.

**What would reverse it.** A configuration large enough that sync latency
becomes the complaint, measured rather than assumed. The fix then is
concurrency in the fetch, which does not require a runtime in the whole tree.

### starlark-rust

**Decision.** Use the `starlark` crate rather than writing an evaluator.

**Alternative.** Write one, which is the only way to guarantee message-for-
message parity with `go.starlark.net`.

**What it costs.** Dialect differences we do not control, including error text;
see §3.11. And a dependency on a crate whose API changes between minor
versions: 0.14 moved `Heap` behind a lifetime and scoped `Module` to a closure,
both of which changed how `ctx` has to be written.

**Why anyway.** Writing a Starlark evaluator is the whole project, not a part
of it.

**What would reverse it.** A dialect difference a component can observe that
the crate will not accept a fix for. M0 found none of that kind.

### The network is the third trait

**Decision.** `meowctl-net` holds a `trait Http`, beside `meowctl-fs` and
`meowctl-exec`, and every request in the program goes through it.

**Alternative.** Give `meowctl-module` an HTTP client directly, and give
`ctx.download` another, which is what `v0.1.0` does: three `*http.Client`
fields on three types.

**What it costs.** A fourteenth crate for one trait and three small
implementations, and one more parameter threaded from the binary. The TLS stack
it pulls in is the same either way.

**Why anyway.** Two crates need it and neither may depend on the other:
`meowctl-module` fetches indexes and tarballs, `meowctl-ctx` implements
`ctx.download`, and they sit side by side under the engine. A shared trait has
to live below both. It also makes two requirements checkable that otherwise
rest on a promise: `OfflineHttp` proves [R-MODULE-043] by construction, and
[R-NET-003]'s HTTPS rule is enforced in one place rather than at each call.

**What would reverse it.** A second consumer never appearing, which would make
it a crate wrapping one dependency for one caller.

## 3. Decided requirements

The requirements where a different answer was available and the argument needs
more than a table row, plus one decision that spans a file rather than a
requirement. The full set of thirty, including those that follow from §2, is
marked in `0.2.0-requirement-tradeoffs.md`.

### 3.1 `$MEOWCTL_CONFIG` — [R-COMMON-020]

**Options.** Resolve the config directory exactly as `v0.1.0` does, or add an
environment variable.

**Trade-off.** A new variable is new surface, and surface is what parity exists
to hold still. Against that, the compat corpus has to point two binaries at the
same configuration for every command it compares, and `--config` on every
invocation makes the harness the thing being tested.

**Chosen.** Add it, because it is additive: a user who never sets it sees
`v0.1.0` behaviour exactly.

### 3.2 Directories created `0700` — [R-FS-004]

**Options.** Reproduce `v0.1.0`, which creates the same config directory `0755`
from `internal/lock/write.go` and `0700` from `internal/state/state.go`, or
pick one.

**Trade-off.** Reproducing an inconsistency is not parity, it is transcription
of a bug. `0700` can break a setup where another user reads the config
directory, which is unusual for dotfiles and would be surprising if it worked.

**Chosen.** `0700`, because the directory holds whatever a user's components
put in it and the narrow default is the safe one.

### 3.3 Dry-run reads see recorded writes — [R-FS-012]

**Options.** Pass every read through to the real filesystem, or answer from
what the dry run recorded.

**Trade-off.** Passing through is simpler and cannot lie about disk. Answering
from the record means a hook that writes a file and reads it back takes the
same branch in a dry run as it will in the real run.

**Chosen.** Answer from the record, because a plan that predicts the wrong
branch is a plan that predicts the wrong run, which is what makes `v0.1.0`'s
dry run something people stopped trusting.

### 3.4 Dry-run predicts failure — [R-FS-033]

**Options.** Let a dry run succeed at everything, or fail where the real run
would fail for a reason visible without performing the effect.

**Trade-off.** Predicting failure risks a false negative that blocks a run that
would have worked. Not predicting it guarantees the opposite error, silently.

**Chosen.** Predict, limited to causes the implementation can see: a write into
a directory that does not exist, a symlink over a regular file with no backup.

### 3.5 The dry-run executor is chosen by phase — [R-EXEC-011]

**Options.** Refuse every subprocess in a dry run; allow a per-call flag; or
decide by phase.

**Trade-off.** Refusing everything makes check hooks useless, because they
interrogate the system. A per-call flag is new Starlark surface and puts the
decision in the component author's hands, where a mistake is silent. Deciding
by phase reuses the set `v0.1.0` already has in `validCheckPhases`.

**Chosen.** By phase, resolved when the executor is constructed, so nothing
below `meowctl-cli` branches on a dry run.

### 3.6 `SuspendOutput` is deleted — [R-EXEC-022]

**Options.** Port the callback, or negotiate terminal ownership through events.

**Trade-off.** The callback works and is small. It also requires the Starlark
layer to hold a function whose purpose is to reach into a renderer, which is
the concrete form of defect #11 and the reason `ctx.Capabilities` knows what a
terminal is.

**Chosen.** Events, and the callback must not exist anywhere in the tree.

### 3.7 Apply-then-undo is a property test — [R-OPS-004]

**Options.** Test the inverses that seem risky, as `v0.1.0` does, or require a
property test over every variant.

**Trade-off.** A property test over `MemFs` costs setup and can be slow enough
to notice. A per-variant test suite is easier to read.

**Chosen.** The property test, because the failure it catches is the one nobody
writes a test for: a variant added later whose inverse is subtly wrong.

### 3.8 A newer `state.toml` is not overwritten — [R-CONFIG-041]

**Options.** Ignore `schema_version`, as `v0.1.0` does, or refuse.

**Trade-off.** Refusing blocks an older binary on a machine that ran a newer
one, which is a real inconvenience during the rewrite when two binaries share a
config directory. Ignoring it means the older binary rewrites the file and
drops whatever it did not understand, which is data loss with no message.

**Chosen.** Refuse. The inconvenience is visible and recoverable; the data loss
is neither.

### 3.9 Starlark is edited by parsing — [R-CONFIG-050], [R-CONFIG-051], [R-CONFIG-052]

**Options.** Port the regular expressions from `internal/rewrite/`, or parse.

**Trade-off.** Parsing costs an AST, a printer that preserves formatting, and
the property tests to prove it does. The regular expressions are forty lines
and work on files the tool wrote.

**Chosen.** Parse. The regular expression carries a documented limitation —
`dep()` must be written `name` before `version` — and a user who hand-edits
their `deps.mod` into the other order gets "not found" for a declaration that
is plainly there. [R-CONFIG-052] follows: a missed edit is reported rather than
written as a no-op, which is what lets `AppendComponent` stop appending
duplicates.

### 3.10 A stale cache is re-fetched — [R-MODULE-042], [R-MODULE-043]

**Options.** Treat a cache mismatch as an error, or re-fetch.

**Trade-off.** An error surfaces tampering loudly. Re-fetching is what a user
wants when the cache was truncated by a full disk or a killed process, which is
the common cause.

**Chosen.** Re-fetch, because the lock is the authority and the cache is a copy.
[R-MODULE-043] pairs with it: a fully cached, verified lock must resolve with
no network, or `meowctl hook shell` hangs on a plane.

### 3.11 Starlark error text is the library's

**Options.** Accept `starlark-rust`'s messages, or translate them to match
`go.starlark.net`.

**Trade-off.** M0 confirmed they differ: "Missing parameter `name` for call to
`component`" against "component: missing argument for name". Translating means
a mapping table that has to track a dependency's internal strings across
versions, and it would be wrong the first time the library adds a message.
Accepting means a user who reads a message from both binaries sees two
wordings, and snapshots have to be taken from the Rust side.

**Chosen.** Accept. The message is not an interface a component depends on, and
`starlark-rust`'s rendering is better: it carries a span and a caret where
`v0.1.0` names a file.

### 3.12 Two handlers claiming one manager is reported — [R-PM-004]

**Options.** Overwrite, as `v0.1.0` does, or report.

**Trade-off.** Reporting can break a configuration that works today by
accident, where a user shadows a stdlib handler with their own and relies on
evaluation order.

**Chosen.** Report, and say so in the release notes. A configuration whose
meaning depends on graph order is not working, it is coincidentally correct.

### 3.13 A filter matching nothing is an error — [R-ENGINE-016]

**Options.** Run nothing, or fail.

**Trade-off.** Failing is unhelpful in a script that filters on a component
that may legitimately be absent on some machines.

**Chosen.** Fail, because `meowctl apply nvim` when the component is spelled
`neovim` otherwise reports success and does nothing, which is the worse outcome
by a wide margin. A script that needs the other behaviour can test first.

### 3.14 Every skip carries a reason — [R-ENGINE-052]

**Options.** Report a skip, as `v0.1.0` does, or require a reason on it.

**Trade-off.** A reason is another field to thread through the event, and the
engine has to distinguish cases it currently merges.

**Chosen.** Require it. "120 components skipped" is the line that made
`v0.1.0`'s dry run useless, and a user cannot act on it.

### 3.15 `--format json` is universal — [R-CLI-006], [R-TUI-032]

**Options.** Port `doctor --json` as the special case it is, or make every
command emit the event stream as JSON.

**Trade-off.** Universal JSON means every event has to be worth serializing and
stays a compatibility surface once anybody parses it.

**Chosen.** Universal, because it costs one sink rather than one flag per
command, and because the compat corpus needs structured output to diff.

### 3.16 Dry-run is not a boolean below the CLI — [R-CLI-011], [R-CTX-014]

Covered by the effects decision in §2; these two requirements are where it is
enforceable in review.

### 3.17 Commands are built per invocation — [R-CLI-012]

**Options.** Keep `var RootCmd = newRootCmd()`, or construct per invocation.

**Trade-off.** A package-level command tree is convenient for tests that reach
in and run a command.

**Chosen.** Per invocation. The convenience is what makes those tests share
mutable state and depend on order.

### 3.18 Version comes from the build, not linker flags — [R-CLI-013]

**Options.** Reproduce the `-ldflags` variable patching, or read build
metadata.

**Trade-off.** Linker flags are what the release workflow already knows how to
set.

**Chosen.** Build metadata, because `mise.toml` currently computes three
`-X` flags in a shell string and a release built outside that task silently
reports `dev`.

### 3.19 A read-only phase gets a `ctx` that cannot write — [R-CTX-030]

**Options.** Leave every phase with the full `ctx`, which is what `v0.1.0`
does, or take the mutating methods away in `install_check`, `upgrade_check`,
`uninstall_check` and `verify`.

**Trade-off.** `v0.1.0` has the machinery for this -- a `RestrictedCtxValue`
and a `ShellCtxAllowList` -- and wires none of it up, so the behaviour is a
change rather than a transcription, and a component that wrote during a check
would start failing.

**Chosen.** Take them away. A check that writes is a check with a side effect,
and the phase names say what they are for. The risk was measured rather than
argued about: no `verify`, `install_check`, `upgrade_check` or
`uninstall_check` hook in `meowctl-stdlib` or in `dotmeow` calls a mutating
method. Revisit if a component turns up with a real need to write during a
check, which would mean the phase split is wrong rather than the restriction.

### 3.20 The lock records which binary wrote it — [R-CONFIG-022]

**Options.** Leave `meta.generated-by` and `meta.updated-at` empty, which is
what every lock `v0.1.0` has ever written holds, or fill them in.

**Trade-off.** Filling them means a lock `v0.2.0` writes differs from
`v0.1.0`'s in two lines, and the byte-identical lock is the strongest evidence
the rewrite has. Leaving them empty keeps that evidence whole and keeps two
declared fields dead.

**Chosen.** Fill them, and exclude `meta` from the comparison in
[R-CONFIG-023]. The fields exist to say which binary last wrote the file, and
the moment that matters is a cutover where two binaries share a configuration
directory -- which is exactly the situation this rewrite creates. Everything a
run depends on stays inside the comparison; the table that is meant to
disagree is the only thing outside it.

### 3.21 Per-file hashes live in the cache, not the lock — [R-MODULE-030], [R-MODULE-044]

**Options.** Fill in `deps.lock`'s `files` table, which `v0.1.0` declares and
never writes, or record the hashes beside the extracted files in the cache.

**Trade-off.** The lock is the more natural home: it is the authority for what
a module resolved to, and a hash in it would be reviewed in a diff. But
`v0.1.0` and `v0.2.0` share a machine during the cutover, and `v0.1.0`'s lock
writer replaces a module entry wholesale, so the hashes would survive until the
first `v0.1.0` run and then vanish without a word. Filling the table also ends
the byte-identical lock that [R-CONFIG-023] and the compatibility corpus check,
which is the strongest evidence the rewrite has.

**Chosen.** The cache, in a file beside `v0.1.0`'s own `.sri` sidecar. The
question the hashes answer is whether the cache still holds what was extracted,
and that is a question about the cache. Revisit once `v0.1.0` is no longer
installed anywhere: then the lock is the better home and the table is already
there.

### 3.22 The remaining decided requirements

[R-OPS-026] forbids a journal during a dry run, where `v0.1.0` has no journal
to forbid; the alternative was a journal of operations that did not happen,
which would replay into damage. [R-TUI-024] puts sub-work on a component's
status line rather than a third indent level, trading detail for the two-indent
rule that makes output scannable. [R-TUI-052] falls back to the default theme
on a malformed theme file rather than failing, because nobody's apply should
stop over colours. [R-TUI-062] fails rather than blocks on a prompt in a
non-interactive session, trading a possible false failure for a CI run that
hangs until it times out, and [R-CTX-026] is where `ctx.prompt` is bound to it
rather than to stdin. [R-TUI-081] requires the capability matrix in
snapshots rather than the handful of cases `v0.1.0` checks, which is affordable
only because the sinks are testable from a fixture stream.
